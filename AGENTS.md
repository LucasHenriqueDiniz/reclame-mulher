# AGENTS.md — Reclame Mulher

Global context for OpenCode agents working in this repository.

## About the project

**Reclame Mulher** is a platform that connects women affected by infrastructure works with the
companies responsible for them. It supports filing complaints, replying to them, a public company
profile, a blog and an admin area.

## Stack

- **Framework:** Next.js 15 (App Router, Turbopack)
- **Language:** TypeScript 5
- **Styling:** Tailwind CSS 3 + shadcn/ui
- **Database:** Postgres (Neon) + Drizzle ORM
- **Auth:** our own, on an HTTP-only cookie + JWT (jose)
- **Forms:** React Hook Form + Zod
- **i18n:** next-intl (pt-BR default)
- **State:** Zustand + TanStack Query
- **Upload:** UploadThing
- **Email:** templates in `email-templates/`

## Environment

- **OS:** Windows 11
- **Shell:** PowerShell (prefer PowerShell/cmd commands; avoid bash-only ones)
- **Node:** through the project's package manager (pnpm, pinned by `packageManager` in `package.json`)
- **Dev port:** 5000
- **Dev host:** 0.0.0.0

## Code conventions

### TypeScript / React
- Use `function` for components (not arrow functions) wherever possible
- Server Actions live in `src/server/` or next to their use in `app/`, with `'use server'`
- Client Components must carry `'use client'` at the top
- Prefer Server Components by default; reach for `'use client'` only when it is needed
  (interactivity, hooks, browser APIs)

### Drizzle / DB
- Every schema change goes: edit `src/db/schema.ts` → `pnpm run db:generate` → `pnpm run db:migrate`
- Never edit a migration that is already applied in production
- Use `db.transaction()` for multi-table operations that need atomicity

### shadcn/ui
- New components: `npx shadcn add <component>`
- Customisations go in `tailwind.config.ts` and `src/app/globals.css`
- Custom components built on shadcn live in `src/components/ui/`

### i18n
- User-visible strings MUST come from `src/messages/pt-BR/*.json`
- Do not hardcode Portuguese text directly in the components

### Auth
- The HTTP-only `auth-token` cookie carries the JWT
- Server Actions and API routes must validate the token through the helpers in `src/server/auth/`
- `middleware.ts` protects routes by role

### Clean Code (adapted)
- **Function limit:** 80 lines (soft), 200 lines (hard)
- **File limit:** 500 lines (soft), 1500 lines (hard)
- **Errors:** validate with Zod; return typed `{ success: false, error: string }` objects from
  Server Actions
- **Naming:** `verb_noun` for actions (`create_user`), `is_`/`has_` for booleans

## Workflow rules

Feature work follows: **pitch → research → plan → implement → postmortem**

1. **Pitch:** write `docs/pitches/<feature>.md` describing the problem, the solution and the scope
2. **Research:** when needed, research and save under `docs/research/`
3. **Plan:** write a detailed implementation plan; get it approved before writing code
4. **Implement:** follow the plan; write the tests alongside the code
5. **Postmortem:** once delivered, write `docs/postmortem/<feature>.md`

Exception: trivial changes (typos, small bugfixes) may skip the pitch.

## Language

Everything written into this repo — code, comments, docstrings, test names, docs, commit messages,
branch names — is in English. What the platform shows its users is Portuguese and stays Portuguese:
UI copy, form labels and hints, validation and error messages that reach a screen, editorial and
blog content, seeded content, `src/messages/**`, and the route folder names listed above. The two
rules do not overlap, and translating product copy is a regression, not a cleanup.

When a comment has to name a Portuguese label, quote the label and keep it byte-identical
(`the "Informações privadas" note`) rather than translating it into something the screen never says.

## Where the rules come from

This repo has **no `.claude/rules/` directory, on purpose.** The house rules are not on disk here;
they are skills of the `hexagram` plugin, installed per machine, at whatever version the person who
cloned it has:

`architecture`, `naming`, `git`, `language`, `testing`, `clean-code`, `diagrams`, `workflow`,
`terraform`, `setup-machine`, `research`, `postmortem`, `lint`.

So a rule that is not written down in this file is not missing — look for it in the plugin. Two
consequences: the rules can move ahead of this repo without a commit here, and a machine without
the plugin installed has no rules at all.

## Commit hook

`.githooks/commit-msg` strips AI attribution trailers from commit messages. Git does not version
`.git/hooks`, so what makes the hook run is one line of local config — and a fresh clone does not
have it. The root `prepare` script sets it on `pnpm install`, and only when nothing else claims it:

```
git config --get core.hooksPath >/dev/null 2>&1 || git config core.hooksPath .githooks
```

If you already point `core.hooksPath` somewhere else, the script leaves your value alone and this
repo's hook stays inert — wire it by hand, or move the file into whatever directory you do use.
